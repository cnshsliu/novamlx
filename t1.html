2. Three Transport Layers — Overview

ACTIVE  TCP Data Plane

Custom binary protocol over TCP. Coordinator sends tensor bytes, worker receives, computes, returns result. Currently used for both control and data.

  • Latency: ~3ms for 16KB tensor send+recv
  • Bandwidth: limited by TCP kernel buffer copies
  • Mature, battle-tested, works reliably
HANGS  Ring (MLX TCP Backend)

MLX's built-in Ring backend. Uses TCP sockets internally but managed by the MLX distributed framework. Requires a JSON hostfile and MLX_RANK env var.

  • Coordinator logs "Rank 0 accepting" then blocks
  • Worker never connects — hangs on init
  • Likely a link-local IPv4 + TCP binding issue
NOT AVAILABLE  JACCL (RDMA)

Apple's JACCL backend uses libibverbs (infiniband/verbs.h) for RDMA over Thunderbolt. Zero-copy, ~5-14μs latency, ~80 Gb/s bandwidth.

  • Requires Thunderbolt 5 hardware
  • Requires sudo rdma_ctl enable on all nodes
  • Requires macOS 26.3+ for large frame support

3. What We Built & Tested

3.1 The Fix: Coordinator Never Initialized Its Own Ring Group

Root cause of the original desync: The code sent initTransport to the worker (which initialized its Ring group), but the coordinator never called RingTransportManager.shared.initializeFromHostfileJSON() on its own side. Both ranks must call init simultaneously for the Ring backend to connect them.

We fixed this in ClusterModelManager.swift:

// AFTER worker acks initTransport:
// Worker is now blocking on Ring init — coordinator MUST init NOW
let ringGroup = RingTransportManager.shared.initializeFromHostfileJSON(hostfileJSON, rank: 0)
if ringGroup.isValid && ringGroup.size > 1 {
    remotePolicy.enableRingTransport()
}

3.2 The Fix: mDNS Hostname → IPv4 Resolution

The worker's hostname was lucass-mac-mini.local (mDNS), which resolves to IPv6 link-local. The MLX Ring backend's TCP sockets fail silently on IPv6. We added resolveHostname() to convert to IPv4 before building the hostfile.

3.3 The Fix: Shard Rebalancing

While testing Ring transport, we also optimized the shard allocation strategy. The spread strategy now minimizes total sequential pipeline latency by giving maximum layers to the fastest node:

4. Ring Backend — Detailed Analysis of the Hang

After fixing the coordinator-init and IPv4 bugs, we re-tested Ring transport. The result: it still hangs. Here's the detailed sequence:

# Coordinator (rank=0, M4 Max)
[ClusterModel] Initializing Ring transport (coord=169.254.85.210:8900, worker=169.254.117.190:8900)
[RemoteShardPolicy] Worker acknowledged initTransport (backend=ring)
[RingTransport] Initializing Ring backend from hostfile JSON (rank=0)...
[ring] Rank 0 accepting                          ← blocks here indefinitely

# Worker (rank=1, M4 Mac Mini)
[WorkerShardService] Initializing transport: backend=ring, rank=1
[RingTransport] Initializing Ring backend from hostfile JSON (rank=1)...
                                                  ← no output after this, blocks silently

MLX Ring Backend Init Sequence (from C++ source)

Looking at ring.cpp in the vendored MLX source, the init logic is:

// RingGroup constructor (ring.cpp:381-438)
size_ = nodes.size();          // 2 nodes
int connect_to = (rank + 1) % size_;  // rank 0 → connect to rank 1

if (rank < connect_to) {       // rank 0 < 1: TRUE
    // Step 1: Accept connections on OUR addresses (rank 0's IPs)
    sockets_left_ = accept_connections(nodes[rank]);
    // Step 2: Connect to rank 1's addresses
    sockets_right_ = make_connections(nodes[connect_to]);
}

The Ring topology connects each rank to its neighbors in a ring: rank 0 connects to rank 1 (right) and accepts from rank 1 (left). For 2 nodes, rank 0 → accepts on its own address, then connects to rank 1.

Why It Hangs

The accept_connections() function (ring.cpp:331) creates a TCP server socket, binds to the address from the hostfile, and calls accept(). The problem is:

Both sides must reach their connection step simultaneously. Rank 0 is blocking on accept() at its own address (169.254.85.210:8900). Rank 1 should be connecting to rank 0, but the worker's log shows it never even prints "Rank 1 connecting" — it blocks before reaching the RingGroup constructor.

Possible reasons the worker blocks before the RingGroup constructor:

  • Hostfile parsing issue — The worker's hostfile JSON might be malformed or the wrong path
  • Ring backend not available — mlx_distributed_is_available("ring") might return false on the worker
  • Environment variable conflict — The worker already has MLX_HOSTFILE or MLX_RANK set from a previous failed init
  • Thread starvation — The worker is already using the Swift cooperative thread pool for the shard service, and the Ring init's C++ thread blocks

5. JACCL / RDMA — Why It's Not Available

Hardware Requirement: Thunderbolt 5

JACCL uses Apple's libibverbs (infiniband/verbs.h) for RDMA operations. The IBV wrapper dynamically loads librdma at runtime:

// vendors/mlx-swift/.../distributed/jaccl/utils.h
struct IBVWrapper {
  bool is_available() {
    return librdma_handle_ != nullptr;  // dlopen("librdma.dylib")
  }
  ibv_device** (*get_device_list)(int*);
  ibv_qp* (*create_qp)(ibv_pd*, ibv_qp_init_attr*);
  ibv_mr* (*reg_mr)(ibv_pd*, void*, size_t, int);  // RDMA memory registration
  // ...
};

Our hardware is Thunderbolt 4 (M4 Max + M4 Mac Mini). RDMA over Thunderbolt requires Thunderbolt 5 hardware:

RequirementCurrentNeeded
Thunderbolt versionTB4TB5
librdma.dylib loadedNoYes
sudo rdma_ctl enableNot applicableRequired on all nodes
macOS version for large framesmacOS 26macOS 26.3+

On our hardware, isBackendAvailable("jaccl") returns true (the code is compiled in), but initialize(strict: false, backend: "jaccl") returns group.size == 0 because IBVWrapper::is_available() returns false — librdma.dylib doesn't exist on TB4 machines.

6. Conclusions

Conclusion 1: Ring Transport Bug is in MLX's C++ Layer

The Ring (TCP) backend hangs during init because the worker process never reaches the connection phase. This is a bug in the MLX distributed framework's Ring backend initialization — likely related to how the C++ code handles the hostfile parsing or socket binding on link-local IPv4 addresses (169.254.x.x). This is not something we can fix at the Swift layer.

Action: File an issue with MLX / test with non-link-local IPs

Conclusion 2: JACCL/RDMA Requires New Hardware

JACCL is the right long-term solution — zero-copy RDMA with ~5μs latency would eliminate the entire TCP overhead. But it requires Thunderbolt 5 hardware. Our M4 Max (TB4) + M4 Mac Mini (TB4) cannot use RDMA. When TB5 Macs are available, JACCL should work out of the box since all the code is already compiled and wired.

Action: Enable JACCL when TB5 hardware is available

Conclusion 3: Current TCP Performance is Near Physical Limit

With shard rebalancing (58/8), the sequential pipeline achieves 9.3 tok/s decode. The breakdown: coord(GPU) ~70ms + TCP ~3ms + worker(GPU) ~36ms = ~109ms. TCP overhead is only ~3% of total time. Even with RDMA (0ms transfer), we'd gain at most ~3% → ~9.6 tok/s. The real bottleneck is GPU compute time, not network.

Action: Focus on speculative decoding or tensor parallelism for next gains
